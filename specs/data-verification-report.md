| 項目 | 詳細 |

| **KPI 範囲** | アポ予定数・アポ消化件数・アポ着座件数・ブリッジ数・決着数・成約件数・残ブリッジ数（全月、全ビュー） |

## 根本原因分析

### 原因 1（最重要）: IMPORTRANGE データ鮮度差

分析シート（`1TGvNaGFosMiiY7m6CZi017XuMAIiD7at1N-1tm-m29k`）はソーススプレッドシートのデータを IMPORTRANGE でコピーして参照している。IMPORTRANGE はリアルタイム同期ではなく遅延更新であるため、アプリがライブのソースシートから直接取得するデータと一致しない期間が生じる。

**証拠**: 2026-04（当月）でアポ予定数の差が +48 件と最大になっている。過去月（2025-09〜2026-03）では差が ±10〜20 件程度に収まっているが、当月は IMPORTRANGE の更新タイミングと新規データ入力のタイミング差が最も開くため。

**修正方法（シート側）**: IMPORTRANGE の更新頻度を高める、または比較時点での IMPORTRANGE のリフレッシュを確認する。**ただし、この問題はアプリのバグではなく、比較対象となる「正解」のスプレッドシートが持つ固有の遅延問題である。**

### 原因 2（重要）: 日付境界条件の実装差（EOMONTH vs Math.trunc）

**シート側**:
```
COUNTIFS(D:D, ">="&EOMONTH(A2,-1)+1, D:D, "<="&EOMONTH(A2,0), ...)
```
生のシリアル数値が EOMONTH の整数値以下かどうかを比較する。日付に時刻コンポーネントが含まれる場合（例: シリアル値 `45931.875` = 9月30日 21:00）、`45931.875 > 45930（9月EOMONTH）` となり **10月に分類される**。

**アプリ側 (`sheets.ts` `serialToDateStr`)**:
```js
const intSerial = Math.trunc(serial);  // 45931 → 9月30日
// → extractYearMonth → "2025-09"
```
`Math.trunc` で整数部のみ取り出すため、同じデータが **9月に分類される**。

**証拠**: 2025-09 の計上売上差が -4,950,000 円（= 5 件 × 990,000 円）、2025-10 が +4,950,000 円（同じ 5 件が 10 月に移動）という完全に逆符号の差分が確認される。同様のパターンが全月で継続する。

**修正方法（アプリ側）**: `serialToDateStr` をシートの EOMONTH ロジックに合わせる：シリアル値が `Math.trunc(serial)` より大きい（時刻コンポーネントあり）かつ月末である場合、翌月として分類する。ただし、これによりアプリとシートの「正解」が一致するかは IMPORTRANGE の鮮度にも依存する。

### 原因 3（設計問題）: クロス集計 決着数 の定義不統一（アプリ内部）

`crossUtils.ts` の決着数:
```js
const SETTLED_STATUSES = ["成約", "失注"];  // ブリッジ不含
```

`summaryUtils.ts` の決着数:
```js
// 成約 + 失注 + (ブリッジ かつ アポ予定日 < Today()-10日)
```

クロス集計ビューと月別サマリービューで「決着」の定義が異なる。シートのクロス集計がどちらの定義に準拠しているかによっては、クロス集計ビューは月別サマリーの決着数と一致しない。

**修正方法**: crossUtils.ts の SETTLED_STATUSES を summaryUtils.ts と統一するか、仕様として両者の定義を文書化する。

### 原因 4（設計確認要）: クーリングオフ込み成約件数の命名と実装の乖離

アプリの実装:
```js
const contract_with_cooling_off = contract_count - cooling_off_count;
```

「込み」＝ "including" を表すなら、成約件数にクーリングオフ件数を **加える** べきと読める。しかしシートとの比較では大半の月で数値が一致（差異は前述の contract_count 差と同値）しており、シートも同様の計算をしている可能性が高い。川畑 亮輔の sheet=-2 はシート側の計算式バグと思われる。命名の意図を確認・文書化することを推奨。
