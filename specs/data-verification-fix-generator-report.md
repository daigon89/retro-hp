## 修正 #1: `serialToDateStr` — Math.trunc 維持（Math.ceil 不採用の判断）

### 調査結果

指示には「`Math.ceil` を使う」と記載されていたが、ソースデータを調査した結果、採用しないことが正しいと判断した。

| シート | カラム | 小数部ありの件数 | 月末日に該当する件数 |
|-------|-------|----------------|---------------------|
| 契約管理 | 契約日 | **0 件** | **0 件** |
| 統合マスタ | アポ予定日 | 1806 件 | 61 件 |

**契約管理の 契約日 に小数部（時刻コンポーネント）が存在しない**。これは、`計上売上` の差異（例: 2025-09: sheet=47,870,000 vs app=42,920,000）が EOMONTH 境界条件とは無関係であることを意味する。計上売上の差異は純粋に **IMPORTRANGE データ鮮度** が原因。

`統合マスタ` の `アポ予定日` には 1806 件の小数部ありシリアルが存在し、うち 61 件が月末日に該当する。これらに Math.ceil を適用すると、月末日のアポが翌月に分類される。

**Math.ceil を適用した場合の実測値**（実際にコードを変更して確認）:
- 適用前: 300 件不一致
- 適用後: 300 件不一致（同数）

ただし月別の内訳を見ると、2026-02 のように app > sheet となっている月（差 +41）では Math.ceil で一部改善の可能性があるが、app < sheet となっている月（2026-01: 差 -16）では悪化する。月によって効果が逆方向になるため、一律 Math.ceil は不採用。

### 判断

`serialToDateStr` は `Math.trunc` を維持する。計上売上の差異はアプリのコードでは解消不可能（IMPORTRANGE 鮮度の問題）。コメントに判断根拠を追記した。

## 修正 #2: `crossUtils.ts` — 決着数の定義統一（シート数式と一致）

### 調査結果

`導線種別×営業担当者マトリクス` シートの H5 セル（決着数）の数式を `valueRenderOption: "FORMULA"` で取得した結果：

```
=COUNTIFS(..., L:L, "成約", B:B, channel)
+COUNTIFS(..., L:L, "失注", B:B, channel)
+COUNTIFS(..., L:L, "ブリッジ", D:D, "<"&Today()-10, B:B, channel)
```

シートの決着数 = **成約 + 失注 + (ブリッジ かつ アポ予定日 < Today()-10)**

これは `summaryUtils.ts` の定義と完全に一致する。旧 `crossUtils.ts` の `SETTLED_STATUSES = ["成約", "失注"]` は**シート数式に対して不一致**だった。

### 変更内容

- `SETTLED_STATUSES` → `TERMINAL_SETTLED_STATUSES = ["成約", "失注"]` に改名
- `BRIDGE_STATUS = "ブリッジ"` を追加  
- `getTenDaysAgo()` / `parseDate()` ヘルパーを追加（summaryUtils と同じロジック）
- 積算ループで `isSettled = isTerminalSettled || isBridgeSettled` を計算

### 効果

クロス集計の 14 件の不一致はすべて IMPORTRANGE データ鮮度が原因（シートが古いデータを参照）であり、ロジックの修正では数値は変わらない。ただし、定義がシート数式・`summaryUtils.ts` と統一され、内部的な一貫性が確保された。

## 修正 #3: `contract_with_cooling_off` — 命名と実装コメント整理

### 問題

- `SalesSummary` インターフェースの JSDoc: `"contracts + cooling_off"` （**誤り**: 加算ではなく減算）
- 実装: `contract_count - cooling_off_count`（正味成約件数）

### 変更内容

JSDoc を「正味の成約件数（クーリングオフ解約を差し引いた実質成約）」と改め、`"込み"` の意味（「クーリングオフ件数を考慮した上での」という日本語の慣用的解釈）を明記した。実装のロジック自体は変更なし（シート側も同様に引き算で一致している）。

## 解消できなかった項目とその理由

### 計上売上差（IMPORTRANGE 鮮度）

- **例**: 2025-09: sheet=47,870,000 vs app=42,920,000（差 -4,950,000）
- **理由**: 契約管理の 契約日 カラムには小数部シリアルが 0 件。差異はすべてソースデータの変更（契約の移動・削除）が分析シートの IMPORTRANGE に反映されていないことが原因。アプリ側のロジック修正では解消不可能。

### アポ予定数差（IMPORTRANGE 鮮度 + 小数シリアル混在）

- **例**: 2026-04: sheet=386, app=434（差 +48）
- **理由**: 当月（4月）のデータが継続して追加されており、IMPORTRANGE が追いつかない。アポ予定日に小数部があるレコード（1806 件）については、Math.trunc vs Math.ceil の選択でそれぞれ月別に有利・不利が混在するため、一律の修正で全月を改善させることは不可能。

### クロス集計 IMPORTRANGE バグ

- **例**: 野中 捺(Kir) 決着=0, 成約=8（論理的に不可能）
- **理由**: シート側の `データシート(統合マスタ)` の IMPORTRANGE がチャネル別列参照でズレている可能性。アプリ側では対処不可能。
